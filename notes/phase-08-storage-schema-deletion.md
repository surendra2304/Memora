# Phase 8 — Relational/vector/event storage, migrations and deletion

**Status:** Baseline review for the 2026-10-07 checkout. Later local fixes and verification are recorded in the post-baseline delta below and in `notes/phase-16-17-iterative-hardening.md`. No production database, PostgreSQL, Qdrant, Redis or Turso was contacted.

## Storage topology and durability

- [FACT] The ORM supports PostgreSQL, Turso/libSQL and SQLite. Default development config is `sqlite:///./data/memora.db`; PostgreSQL uses `pool_size=10`, `max_overflow=20`, pre-ping and a 3-second connect timeout (`core/config.py:16-30`; `storage/relational/session.py:99-172`). SQLite enables WAL, `busy_timeout` (default 30 seconds), and `synchronous=NORMAL` (`:60-97`).
- [FACT] Storage receipts distinguish `postgresql`/`turso` as `shared_durable` from SQLite as `process_local`; production `storage_ready()` is false unless the active backend is marked durable. If the configured PostgreSQL or Turso connection falls back to SQLite in production, `get_db()` refuses requests with 503 rather than serving non-authoritative local writes (`storage/relational/session.py:20-34,110-172,184-198`).
- [FACT] Local vector mode stores vectors in a process-local dictionary; Qdrant calls are tenant-filtered. When Qdrant is unavailable in production, vector upsert raises and deletion returns false (`storage/vector/qdrant_adapter.py:27-41,85-146,148-175,188-234`). The canonical writer catches vector-upsert failures and can still commit the relational memory with `vector_indexed=False` (Phase 6).
- [FACT] Graph relationships are rows in the relational `memory_relationships` table with endpoint foreign keys; no separate graph database adapter was found (`storage/relational/models.py:233-255`). Redis is used by the event emitter for Pub/Sub only; no runtime cache adapter was found in `apps/`, `core/` or `storage/` (`core/events/emitter.py:38-69`; `rg` runtime scan).

## Schema and migrations

- [FACT] The checked-in migration chain has 9 linear revisions: `8a8f529e1cdb` → `9cf9d4184551` → `1218edca5327` → `433bb01f2a2a` → `5e89a1b2c3d4` → `b1206b9e4a61` → `c2407f92e1ab` → `d7f1c93ab210` → `e4a1c7f90b23` (`migrations/versions/*.py`). `migrations/env.py` loads current model metadata and uses SQLite batch mode (`migrations/env.py:8-20,21-58`); Alembic is configured under `migrations/` (`alembic.ini:1-6`).
- [FACT] The application lifespan calls `Base.metadata.create_all()` rather than `alembic upgrade`; `create_all` creates absent tables but does not alter existing tables (`storage/relational/session.py:177-182`; `apps/api/main.py:148-157`). Several recent revisions explicitly contain convergence logic for pre-existing ORM-created tables (for example `migrations/versions/b1206b9e4a61_add_durable_event_feed.py:7-24` and `migrations/versions/d7f1c93ab210_scope_idempotency_to_agent.py:23-28`).
- [FACT — local verification] A migration-only scratch upgrade/downgrade/upgrade round trip passed earlier (Phase 0). A separate scratch check first ran current `Base.metadata.create_all()` on an empty SQLite database and then `alembic upgrade head`; the upgrade failed at `9cf9d4184551` with `OperationalError: table access_grants already exists`. This directly demonstrates a fresh-app-startup/create-all database cannot subsequently be treated as an Alembic base without a baseline/stamp or convergence handling for earlier revisions. Scratch files were temporary and discarded.
- [FACT] `MemoryRecord` stores content as ordinary SQL `Text` and provenance/entities as JSON, with tenant and identity-scope indexes and a composite idempotency unique index (`storage/relational/models.py:158-228`). Audit and event rows are also relational (`:257-338`).

## Deletion and convergence

- [FACT] `DELETE /v1/memories/{id}` defaults to soft deletion; `?hard=true` calls the hard-delete workflow (`apps/api/routers/v1_memories.py:619-635`). Soft delete transitions the record to `DELETED` and commits, but does not remove its vector (`core/memory/service.py:524-535`). Search excludes deleted states by default, but the direct ID getter does not filter lifecycle (`core/memory/service.py:192-219`). [INFERENCE] A soft-deleted memory remains in relational storage and the Qdrant/vector mirror, and an owner who knows the ID can still retrieve it through the direct getter unless another policy rule denies access.
- [FACT] Hard delete creates a tombstone, attempts vector deletion, deletes relational graph relationships, marks `cache_deleted=True`, removes the relational record, and commits tombstone/audit (`core/memory/service.py:467-516`; tombstone convergence requires all four flags, `storage/relational/models.py:282-305`). The endpoint publishes its `memory.updated` event only after that service commit (`apps/api/routers/v1_memories.py:627-635`).
- [FACT] No cache adapter or purge call is present in the hard-delete path; `cache_deleted=True` is assigned unconditionally (`core/memory/service.py:489-503`). [INFERENCE] The tombstone's cache-convergence flag is currently bookkeeping rather than evidence of a cache purge.
- [FACT] `SelfHealingSupervisor` checks five conditions and caps each repair at 500 rows (`core/resilience/self_healing.py:85-113`). Its orphan-vector check examines only the adapter's in-process `_mock_store` (`:177-225`), not a Qdrant collection listing; tombstone retry only attempts vector deletion (`:116-175`). [INFERENCE] Existing Qdrant points absent from the process-local mirror (especially after restart) are outside this orphan scan; failed non-vector flags have no repair path here.
- [FACT] The vector delete happens before the relational delete/tombstone commit (`core/memory/service.py:481-516`). [INFERENCE] If the remote vector delete succeeds but the later relational transaction rolls back, vector and relational state can diverge with no committed tombstone to drive repair.
- [FACT] `get_memory_by_id` selects by ID without checking lifecycle state (`core/memory/service.py:192-219`), while query/search defaults exclude `DELETED` unless a query explicitly asks to include deleted records (`core/memory/service.py:287-302`). This makes “soft delete” a search exclusion, not data erasure.

## Events, replicas and external data paths

- [FACT] `EventEmitter.publish(..., db=db)` inserts an `EventLog` row in the caller's SQL transaction and only notifies in-memory history/Redis after commit; rollback drops queued notifications (`core/events/emitter.py:71-109,184-202`). In-memory history is bounded to 500 events (`:38-47`). Redis Pub/Sub is not the durable event store.
- [FACT] `EventLog` has tenant, target-agent, payload, cloud-sync status and an increasing ID cursor; consumer cursor uses `(tenant_id, agent, consumer_id)` (`storage/relational/models.py:311-338`). The API allows only selected payload keys to readers (`apps/api/routers/v1_events.py:45-63,138-185`) and supports acknowledgement only for the next visible event (`:210-246`). However, read/cursor/ack endpoints currently hard-code `tenant_id="default"` (`:147-149,197-207,217-245`); the source comment says this remains shared until credentials map to tenants.
- [FACT] Optional Turso event storage creates its own event/cursor schema, appends JSON event payloads and reads by tenant/recipient (`storage/relational/turso_events.py:21-35,74-88,104-151,164-183`). The emitter submits unsynced local events after commit and polls a retry queue every 30 seconds (`core/events/emitter.py:118-176,184-193`).
- [FACT — external data path] If `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN` are set, the canonical write path asynchronously sends memory `content_text` and selected fields to Turso (`storage/relational/turso_sync.py:61-105,108-152`; invoked after write commit in `core/memory/pipeline/write_service.py:466-471`). The export omits most identity-scope and provenance fields (`:117-145`). Startup import is opt-in or production-triggered and selects/imports memory content but reports `deletions: 0` (`apps/api/main.py:41-68,148-154`).
- [INFERENCE] A Turso write-through copy is not covered by the local deletion tombstone: hard delete has no Turso delete call, while the startup import is merge-only and does not propagate remote deletions. Depending on the selected primary/replica configuration, stale remote copies may persist and could be re-imported. This was not tested against Turso.
- [FACT — privacy] Context generation persists `task_query` in a `context.generated` event (`core/memory/context/builder.py:268-276`); configured Turso event sync sends the full stored payload (`core/events/emitter.py:130-139`). The event-feed response allowlist omits query, but that is separate from local/remote persistence. **No Turso, Redis, Qdrant, PostgreSQL or other external service was contacted during this review.**

## Exit check

- [FACT] The active durable source of truth is the configured ORM backend; vector points and optional Turso/event replicas are separate stores. The event bus has a bounded local memory view and optional Redis/Turso integrations; Redis is not an application cache here.
- [FACT] Migration-only round-trip verification and app-create-all-then-migrate verification produce different outcomes; the latter fails on a fresh schema. Phase 8 is complete; next is SDKs/adapters and cross-agent contracts.

## Post-baseline delta — 2026-10-08

- A fresh database created through `init_db()` now gets an Alembic `head` stamp only when the pre-create database had no Memora tables and no `alembic_version`. Existing unversioned databases are not auto-stamped, because doing so could skip required data transformations. `tests/test_schema_init_migrations.py` compares the fresh ORM schema's tables, columns, and uniqueness invariants with a migration-only SQLite upgrade, and confirms a subsequent `alembic upgrade head` succeeds.
- A temporary installed-wheel run verified the packaged `init_db()` path creates/stamps SQLite at `f35ecb0a7c12`, then the packaged Alembic CLI reports the same head from outside the source checkout. Docker CLI/image and hosted DB migration behavior remain unverified.
- Subsequent hardening added `DeletionTombstone.turso_deleted` and remote anti-resurrection fencing/retry, direct-read lifecycle enforcement, Qdrant tenant-filtered paged orphan reconciliation, and event-ID tenant/publisher collision checks. These fixes are locally tested; no remote Turso/Qdrant/Redis/PostgreSQL service was contacted. Event-feed APIs still bind to the shared `default` tenant until credentials carry tenant claims.
