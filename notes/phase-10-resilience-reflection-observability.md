# Phase 10 — Resilience, reflection, collaboration and observability

**Status:** Complete (static review). No application source changed, no tests run in this phase, and no cloud/Redis/Qdrant/Turso calls were made by this review.

## Runtime lifecycle and background work

- [FACT] API lifespan initializes the relational DB, optionally imports data from Turso at boot, connects Qdrant and Redis, starts a Turso event-sync loop when configured, then stops that loop on shutdown (`apps/api/main.py:41-72,148-165`). In production, startup logs an error if the durable event store is not configured (`apps/api/main.py:157-161`).
- [FACT] There is no Celery/RQ/APScheduler/cron/background-job scheduler in the runtime source scan. Reflection and decay are request-triggered. The only periodic runtime thread located is event sync (30-second default; `core/events/emitter.py:162-181`).
- [FACT] A successful canonical memory write also starts one daemon `threading.Thread` per memory to perform a non-blocking Turso write-through when both credentials are present (`core/memory/pipeline/write_service.py:462-471`; `storage/relational/turso_sync.py:108-152`). Failures are logged at debug and have no retry loop in that worker (`storage/relational/turso_sync.py:95-105`). [INFERENCE] A burst of writes can create an unbounded number of short-lived sync threads; this is not a bounded worker queue.

## Circuit breakers and repair supervisor

- [FACT] The process registry contains a `qdrant` breaker created by `QdrantVectorAdapter`, configured by `MEMORA_QDRANT_FAILURE_THRESHOLD` (default 3) and `MEMORA_QDRANT_RECOVERY_SECONDS` (default 30) (`storage/vector/qdrant_adapter.py:27-41`). The breaker has CLOSED/OPEN/HALF_OPEN states and locks its state (`core/resilience/circuit_breaker.py:35-49,93-115,123-129`).
- [FACT] Qdrant upsert and delete use the breaker (`storage/vector/qdrant_adapter.py:125-146,158-175`), but `connect()` and `search_similarity()` do not (`:60-76,188-234`). No Redis or Turso call site was found using the registry. [INFERENCE] Search failures do not open the Qdrant breaker, and the breaker is not a uniform wrapper around all optional dependencies.
- [FACT] The HALF_OPEN code reads the state and sets a local `probing` boolean, then releases the lock before making the call; it has no shared in-flight-probe reservation (`core/resilience/circuit_breaker.py:164-191`). [INFERENCE] Concurrent callers can all pass during HALF_OPEN despite the comment promising one probe, so recovery traffic may stampede the dependency.
- [FACT] `/health` reports SQL `SELECT 1`, Turso event-store probe/configuration and vector readiness, returning 200 or 503 (`apps/api/routers/health.py:14-54`). Qdrant `readiness()` returns connected/available based on `_initialized` and explicitly exposes breaker state separately (`storage/vector/qdrant_adapter.py:43-58`). [INFERENCE] An initialized Qdrant client whose breaker has opened can still be reported available by `/health`; health does not inspect the registry, Redis, or event-sync thread.
- [FACT] `SelfHealingSupervisor` runs five checks: unconverged tombstones, orphaned vectors, dangling supersession pointers, open circuits, and decay backlog; it catches per-check exceptions, caps most repairs at 500, and defaults to dry-run (`core/resilience/self_healing.py:85-113,116-175,177-260,262-323`). The API allows any authenticated agent to preview, but only `memora` to execute repairs or manually reset a circuit (`apps/api/routers/v1_resilience.py:25-35,69-118`).
- [FACT] The orphan-vector check reads `vector_adapter._mock_store`, not a Qdrant enumeration API (`core/resilience/self_healing.py:177-225`). Qdrant adapter code mirrors successful IDs/vectors in that process-local dictionary (`storage/vector/qdrant_adapter.py:31-34,125-146`). [INFERENCE] It cannot independently reconcile all remote vectors after process restart and is not a remote-store inventory check.
- [FACT] `check_decay_backlog` counts only ACTIVE and VERIFIED records older than 7 days and above a configurable importance threshold (`core/resilience/self_healing.py:291-323`), while the decay engine operates on ACTIVE and CANDIDATE records and applies an age gate of 14 days by default (`core/lifecycle/decay.py:14-43,65-73`). [INFERENCE] The preview can count 7–13-day records and VERIFIED records that the default decay run will not process, and it omits CANDIDATE records that the decay run can process.
- [FACT] Findings are evaluated before repair and orphan/dangling check results remain `healthy=False` when findings were present, even if the repair loop succeeds (`core/resilience/self_healing.py:169-175,219-225,254-260`). [INFERENCE] A repair response's `healthy` field describes initial findings for those checks, not necessarily post-repair convergence; callers should inspect both `findings` and `repaired` and rerun to verify.

## Reflection and lifecycle maintenance

- [FACT] The reflection engine runs five deterministic analyses—recurring themes, numeric contradictions, stale high-importance memories, knowledge gaps, and agent specialisation—over at most the newest 5,000 ACTIVE/VERIFIED rows per tenant, returning at most 20 results per analysis (`core/reflection/engine.py:142-156,159-200,203-223,233-287,289-348,350-441,443-486`). It excludes its own prior reflection records from the corpus, and uses `kind:subject` fingerprints to avoid storing duplicate conclusions (`:225-231,489-505`).
- [FACT] `/v1/reflection/run` defaults to a dry run; only the authenticated `memora` identity may persist results. Any authenticated agent may read `/v1/reflection/insights` (`apps/api/routers/v1_reflection.py:25-64`). The listing query filters memory type and reflection provenance but does not constrain `tenant_id` (`:57-79`); the run endpoint invokes the default `tenant_id="default"` (`core/reflection/engine.py:159-165`).
- [FACT] Insight persistence creates `MemoryRecord` ORM rows directly and commits; it does not call `MemoryWriteService` (`core/reflection/engine.py:507-544`). [INFERENCE] Stored reflections do not pass through the canonical write scanners/audit/vector-embedding path, unlike regular v1 writes.
- [FACT] The gap analysis queries event types `memory.query`, `query`, and `context.build` (`core/reflection/engine.py:387-421`), while the current context builder emits `context.generated` with a `query` field (`core/memory/context/builder.py:265-276`); no `memory.query`, `query`, or `context.build` emitter was found in `core/` or `apps/api/`. [INFERENCE] Normal context-generation traffic does not feed the current gap-analysis query; absent another producer, that insight kind will usually lack repository-generated evidence.
- [FACT] Reflection functions fail independently: an exception is logged and the DB session rolled back, then the remaining analyses continue (`core/reflection/engine.py:186-192`). [INFERENCE] A partial report can be returned without a top-level failure status; logs are needed to distinguish “no insights” from a failed analysis.
- [FACT] Decay is only exposed as a manually triggered `/v1/memories/decay` endpoint (`apps/api/routers/v1_memories.py:641-657`); no scheduled job invokes it. The route requires an authenticated agent but has no service-admin check and does not pass a tenant to `MemoryDecayEngine.apply_time_decay`, whose default is `tenant_id=None` (all tenants) (`core/memory/service.py:633-647`; `core/lifecycle/decay.py:14-41`). [FACT] The worker commits each batch (`core/lifecycle/decay.py:107-108`). [INFERENCE] Any authenticated caller can initiate a mutating, cross-tenant decay sweep; this endpoint has a broader mutation boundary than reflection and resilience repair.

## Collaboration contracts

- [FACT] Three collaboration endpoints exist: `/assist`, `/contribute`, and `/delegate`; assistance requests are capped at 25 candidates and contribution grants can be bounded to 30 days, defaulting to 24 hours (`apps/api/routers/v1_collaboration.py:29-93,96-123`; `core/collaboration/service.py:119-150,285-361`).
- [FACT] Assistance returns results the requester can already read and identifies additional candidates from grants/role/description without reading candidate-private content (`core/collaboration/service.py:137-184,186-283`). Contribution checks that the caller owns the memory and creates an expiring access grant (`:285-351`).
- [FACT] The collaboration “delegate” path registers a bounded sub-agent, writes an audit decision, commits, and returns a `status="delegated"` object (`core/collaboration/service.py:363-407`). It does not enqueue, invoke, or deliver the `task_description` to a worker. [INFERENCE] It is identity/scope bookkeeping, not asynchronous task execution.
- [FACT] Assistance's granted-owner aggregation passes `db.query(MemoryRecord).count()`—an unfiltered scalar count—alongside `owner_id`, then groups by owner (`core/collaboration/service.py:195-208`). [INFERENCE] The displayed `evidence_count` is not a per-owner count; every returned owner can receive the same global count, distorting candidate ranking.

## Events, durability and delivery

- [FACT] `EventEmitter.publish()` adds an `EventLog` row to the caller's SQLAlchemy transaction only when passed `db`; after commit, listeners expose it in the bounded process-local history and optional Redis Pub/Sub. If no DB is passed, it notifies locally/Redis without writing `EventLog` (`core/events/emitter.py:71-116,184-204`).
- [FACT] API startup starts a 30-second poller when Turso event credentials/configuration are present; after-commit hooks also submit immediate per-event Turso sync work through a two-worker executor (`core/events/emitter.py:118-181,184-202`). Production event-feed reads fail closed with 503 when Turso is not configured or is unavailable (`apps/api/routers/v1_events.py:138-166`).
- [FACT] The feed provides ordered polling, per-agent consumer cursors and explicit acknowledgement; reads alone do not advance a cursor. Payloads are projected through a 10-event-type field allowlist (`apps/api/routers/v1_events.py:41-63,138-246`). Both SQL and Turso paths hardcode the shared `default` tenant (`:147-154,197-246`), consistent with the code comment that API keys currently identify services, not tenants.
- [FACT] `/mesh/envelope` validates sender/recipient names, timestamps and TTL (maximum 86,400 seconds), caps serialized payloads at 256 KiB, requires production signatures, and validates HMAC-SHA256 signatures; Futuris forecast and Stratex decision event types have additional advisory/paper-only field checks (`apps/api/routers/v1_events.py:249-300`). Events are persisted remotely first when Turso is configured, then locally (`:302-334`). [INFERENCE] Remote and local persistence are not one atomic transaction; a later local DB failure can leave a remote event without a matching local row.

## Metrics and health evidence

- [FACT] The process-wide metrics collector retains rolling samples in deques of up to 1,000 observations and cumulative counters in memory; it exports JSON plus 10 Prometheus metrics (`core/metrics/collector.py:11-31,82-120,122-160`). Values reset with process restart and are not shared across workers.
- [FACT] Write, policy, context-budget, compaction, predictive-hit and cross-encoder-latency paths update selected counters (`core/memory/pipeline/write_service.py:268-290,480-489`; `core/policy/engine.py:239-249`; `core/memory/context/builder.py:187-188,224-226,265-276`; `core/memory/context/reranker.py:74`). [FACT] No production caller of `record_retrieval()` was found, and all `record_write()` call sites explicitly pass `is_contradiction=False` (`core/metrics/collector.py:47-53`; `core/memory/pipeline/write_service.py:268-290,480-489`). [INFERENCE] Retrieval relevance/staleness and contradiction-rate telemetry can remain at zero despite real traffic; these advertised SLI values are not currently backed by the relevant call sites.
- [FACT] `/v1/metrics`, `/metrics`, `/health` are mounted without authentication dependencies (`apps/api/routers/v1_metrics.py:9-20`; `apps/api/routers/health.py:14-18`). [FACT] Health performs a live SQL probe, may perform a Turso live probe, and reports vector readiness (`apps/api/routers/health.py:18-54`). The metrics routes expose aggregate counters/timing summaries without per-agent labels.

## Exit check

- [FACT] Resilience, repair, reflection, collaboration, event feed and metrics are implemented as request-accessible components; only Turso event synchronization is periodic in the API runtime. Decay/reflection/repair have no automatic scheduler.
- [FACT] Static review identified a mutating decay endpoint callable by any authenticated principal across tenants, health/telemetry omissions, incomplete breaker coverage, reflection-input mismatch, direct reflection persistence, misleading candidate counts, and limits in vector reconciliation. These are recorded for later verification/risk ranking; they were not dynamically probed in this phase.
